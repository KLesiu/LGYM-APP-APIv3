# LgymApi.Infrastructure.csproj

- Purpose: technical implementations.
- Contains: EF Core `DbContext`, migrations, Unit of Work, storage, remaining technical services, Hangfire persistence, and module-owned infrastructure DI helpers.
- Rules: repositories must not call `SaveChangesAsync` or own transactions.
- Boundary: do not register Application services here.
- DI ownership: `AddInfrastructure(...)` composes shared `AppDbContext` and module-context aliases, UoW, mapper registry, Hangfire persistence/server selection, post-commit dispatch, and the remaining Training Planning, Workout & Progress, Coaching, Nutrition, and Reporting persistence adapters. It does not register extracted module services or providers.
- `AddNotificationsInfrastructure()` registers only the scoped email-lease settings bridge over shared background-command options. Notifications owns the single `EmailOptions` instance, `IEmailSender` factory, six template composers, Dummy-versus-SMTP selection, and FCM provider through its configured module facade.
- Composition: the API invokes only `AddInfrastructure(...)`; the narrower technical helpers remain Infrastructure-owned decomposition seams and are not called directly by the host.
- Hangfire PostgreSQL storage and server registration remain Infrastructure-owned. `AddInfrastructureBackgroundServer()` is the public technical seam called only by the final Worker facade when the host enables the background server; the API does not call the helper directly.
- Infrastructure compiles the Domain- and resource-dependent Worker runtime implementations under their established `LgymApi.BackgroundWorker.*` namespaces. The Worker assembly remains the public registration and recurring-job composition facade, so the frozen Worker graph does not require Domain or Resources edges.
- Exercise persistence maps the ELO profile as a string column with `Standard` as the database default for new rows.
- **Persistence Updates**: Added `EmailNotificationStatus.Sending = 3` (explicit numeric value) to support exactly-once delivery guards. Added `NotificationMessage.DeliveredAt` (nullable DateTimeOffset) for crash-safe delivery tracking. Notification send claims now stamp `Status=Sending` and `LastAttemptAt` in one atomic update so interrupted claims do not leave unrecoverable `Sending` rows.
- Push installations are persisted as installation-scoped rows with a unique `InstallationId`, optional `UserId` and `SessionId`, mutable FCM token/app metadata, and disablement metadata used for unregister/logout/account-switch flows. Logout forwards an account-session marker through Notifications contracts; `PushInstallationRepository` alone rebinds it to the persisted `UserSession` ID and stages disassociation without saving.
- Push delivery persists `PushNotificationMessage` rows with payload metadata (`schemaVersion`, `type`, `eventId`, optional entity linkage), sanitized provider response markers, retry timestamps, failure classification, and temporary scheduler reservations used for atomic cross-instance enqueueing. Notifications owns the FCM provider, configuration, retry mapping, and provider settings; Worker owns environment-selected scheduling.
- Notifications owns its five stage-only persistence implementations and mappings behind `INotificationsPersistenceContext`; Infrastructure retains the scoped context alias, fixed global registrar phase, migrations, and a narrow internal email-lease settings bridge. FCM delivery is an internal Notifications implementation; provider credentials, raw installation tokens, raw provider response bodies, EF entities, and provider implementation details stay outside public contracts. See [`issue-381-notifications-boundary.md`](../docs/modular-monolith/issue-381-notifications-boundary.md).
- Infrastructure has no FCM provider registration or package ownership. Notifications resolves raw registration tokens only within its private provider implementation; Application, Worker, Common, and API contracts must not expose those tokens or FCM credentials.
- The FCM provider extraction changes no provider behavior, project references, endpoints, `AppDbContext`, migration stream, or physical entity location.
- Push infrastructure now separates `PushNotifications:SendEnabled` from registration and uses `LastSeenAt` plus recurring cleanup thresholds to mark stale installations as disabled without deleting audit rows.
- `UserExternalLoginRepository` keeps Google unlinking on the existing soft-delete path: it can load the active Google login for a user and stage `IsDeleted=true` so the provider subject can be linked again later.
- `AppDbContext` is the persistence composition root only: it owns `DbSet` exposure, global typed-ID conventions/converters, soft-delete filter application, the explicit registrar call, role seed application, and the timestamp save pipeline.
- `AppDbContext` explicitly implements the internal Platform, Identity, Training Planning, and Notifications persistence contexts. `AddPlatformPersistence(...)` aliases each context to the same scoped `AppDbContext`; module seams do not expose save, transactions, a database facade, generic entry, or foreign-owned sets.
- Entity-specific EF mappings now belong in module-owned `Data/Configurations/<Module>/*EntityTypeConfiguration.cs` classes and must not be reintroduced inline in `AppDbContext`.
- `Data/Configurations/AppDbContextEntityTypeConfigurationRegistrar` remains an explicit fixed-order registrar that runs after global typed-ID/filter conventions and before seed data; preserve its manual ordering and do not replace it with assembly scanning or reflection-order registration.
- The registrar runs the 48 configurations once in this order: Identity, Training Planning, Workout & Progress, Platform Reference Data, Coaching, Notifications, Platform reliability, Nutrition, Reporting. Identity's first phase is supplied by its internal registrar; Infrastructure retains the fixed phase coordinator.
- `AppDbContextFactory` is the sole production design-time factory. It constructs the shared Npgsql `AppDbContext` directly, without API or runtime DI, and resolves the existing Infrastructure migration assembly and `AppDbContextModelSnapshot`.
- Design-time tooling prefers `LGYM_MIGRATION_POSTGRES`; its localhost fallback is Development-only. Runtime Hangfire storage never prepares its schema, and the runtime connection validator rejects elevated roles, multiplexing, missing grants/schema, and configured RLS mismatches without logging credentials.
- Reporting/photo persistence mappings live under `Data/Configurations/Reporting/*EntityTypeConfiguration.cs`, while the five notification mappings live under `LgymApi.Notifications/Persistence/Configurations`. Platform owns its AppConfig and reliability configurations, while Infrastructure retains the fixed registrar, global typed-ID conventions, `AppDbContext`, and migration stability responsibilities.
- Persistence ownership is defined by the executable `LgymApi.ArchitectureTests/PersistedEntityOwnershipCatalog.cs`. The single `AppDbContext`, database, and migration stream remain technical composition roots, not shared write ownership.
- Known internal entity IDs use `Id<T>` and are stored through EF Core as PostgreSQL `uuid` provider columns. HTTP and JSON UUID values remain strings. Only `PushNotificationMessage.EntityId` and `PushEventPayload.EntityId` are polymorphic string ID exceptions.
- Repositories stage changes only. Application services own `SaveChangesAsync()` and explicit transaction commit or rollback; PostgreSQL transaction tests prove both commit visibility and rollback cleanup from fresh contexts.
- Runtime persistence adapters must use provider-neutral EF Core APIs. Raw SQL and branching on `Database.ProviderName` or provider-name string literals are prohibited.
- `EfActorRowSecurityScopeFactory` is the sole runtime RLS seam. It starts the existing UoW transaction, parameterizes transaction-local PostgreSQL `set_config('lgym.account_id', ..., true)` on its active Npgsql connection, returns the existing InMemory no-op transaction, and disposes setup failures without clearing EF tracking.
- Training Planning owns its four stage-only persistence registrations and three EF configurations. Infrastructure retains the shared scoped `ITrainingPlanningPersistenceContext -> AppDbContext` bridge, fixed registrar phase invocation, and the Task-15 `IPlanDayPersistence` composition adapter; it does not implement Planning repositories or the active-plan pointer.
- `UserRepository.GetByIdsAsync` is the active-only, no-tracking Identity batch lookup used by Application account facts. It accepts the caller token, returns each active database match once without ordering guarantees, and never saves or opens a transaction; Application restores caller order and duplicates.
- `AddCoachingInfrastructure` registers the sole focused invitation, active-link, unpaged fact-reader, and trainee-note/history persistence adapters. They use only the existing Coaching DbSets, map through Application's registered mapper, and stage inserts or detached note-state updates without commits or transactions so Application can commit a note and its history together. Identity enrichment, filtering, sorting, counting, and paging remain Application concerns.
- Nutrition Infrastructure registers the module-local `IDietPlanPersistence` and `ISupplementationPersistence` adapters. Their read methods are explicitly no-tracking, mutation loads are tracked, and all writes remain staged for the owning Application use case's one UoW save; adapters never save or start transactions.
- Reporting Infrastructure registers five focused adapters under `Repositories/Reporting` for templates, requests/submissions, recurring assignments, photos/upload sessions, and relationship access. `ReportingPersistenceAccountIds` is the sole Reporting seam that rebinds marker-safe `Id<AccountReference>` values to persisted `Id<User>` foreign keys; the adapters never save or own transactions.
- Local Development photo URLs are HMAC-SHA256 bearer capabilities over version, HTTP method, normalized storage key, and Unix expiry. Development Local startup requires a dedicated minimum-32-byte key; Testing uses an ephemeral process key when none is supplied, and non-Local providers keep capability verification disabled. Local uploads enforce configured MIME and actual streamed byte limits, write to same-directory temporary files, and publish only by atomic move.
- `20260801222135_RepairRecurringReportAssignmentRequestIndex` is the discoverable forward Reporting migration. Its defensive `Up` drops and recreates `IX_ReportRequests_RecurringReportAssignmentId` as non-unique; the historical orphan repair file remains unchanged. Its `Down` deliberately throws because restoring uniqueness after multiple request-history rows is unsafe.
- `RecurringReportAssignmentPersistenceRepository.FindByIdForUpdateAsync` is a caller-transaction-required, stage-only operation. It uses a provider-neutral EF Core no-op update of `UpdatedAt` for the matched non-deleted row, then reloads the complete no-tracking graph for fresh eligibility evaluation. The adapter never opens a transaction or saves changes.
- Workout & Progress Infrastructure registers seven focused adapters under `Repositories/WorkoutProgress`. `WorkoutPersistenceAccountIds` is the sole seam that converts marker-safe `Id<AccountReference>` values to and from persisted `Id<User>` foreign keys; adapters stage writes and never save or own transactions. The remaining legacy Exercise and Training repositories are consumed only by Workout-owned Planning-port adapters in Application.
- The six Nutrition entities, existing EF configurations and filters, `AppDbContext`, fixed configuration registrar, PostgreSQL database, and single migration stream remain unchanged by the focused Nutrition cutover.
- The guarded project graph changes no persistence, migration, schema, provider, or DataSeeder behavior.
- `20260807160000_AddTutorialRowSecurityPolicies` installs explicit parent and child tutorial policies while deliberately leaving RLS disabled and the model snapshot unchanged. `deploy/postgres/activate-tutorial-row-security.sql` is a manual staging-only, advisory-lock-protected activation; its paired deactivation script removes FORCE/ENABLE state without removing policies or data. The container runtime template records the dormant policy contract with both RLS flags false.
- The canonical operator procedure, diagnostics, staging exit criteria, and break-glass rollback are in [`tutorial-rls-pilot.md`](../docs/security/tutorial-rls-pilot.md). Production continues to expect disabled RLS until a separate go/no-go changes configuration and database state together before traffic.
