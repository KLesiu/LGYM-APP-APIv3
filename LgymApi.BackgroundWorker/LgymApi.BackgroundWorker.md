# LgymApi.BackgroundWorker.csproj

- Purpose: Hangfire/background worker implementations for Application contracts and the bounded Common seam.
- Contains: persisted job implementations, the closed command runtime and handlers, scheduler adapters, and Worker DI.
- Rules: keep jobs idempotent where practical and register worker services in the worker module.
- Boundary: do not let the worker module become a second composition root for the API.
- Composition: the API invokes the Worker facade last, after module, remaining Application, Infrastructure, and API-adapter facades. Worker registers runtime jobs, handlers, dispatch adapters, and environment-selected schedulers without re-registering module services, repositories, or providers.
- Durable commands: Worker owns the injected closed 15-command registry. It writes legacy Common command IDs as canonical IDs, accepts Application CLR full names only as read aliases, and does not scan loaded assemblies for command types.
- Runtime contracts: Worker owns the typed background-action resolver and dispatch/orchestration boundary, which hides DI scopes behind exact handler-name lookup. Application owns command-envelope lifecycle runtime commits. The Worker DI helper registers one closed 15-row command registry, the 16 exact handlers, the Application dispatcher port, and validates handler cardinality after registration.
- `CommandOutboxWriter` implements Application's stage-only command-envelope port with the same registry, serialization, and deterministic-correlation rules as `CommandDispatcher`; it stages only and leaves commit and later committed-intent scheduling to the caller/runtime flow.
- Accepted report progress uses the production outbox path: Reporting stages `ReportSubmissionAcceptedProgressCommand` before its submission commit, then committed-intent and `ActionMessage` infrastructure forward its shared JSON payload to Workout & Progress. The Workout owner validates its raw wire representation and maps it to its own consumer event; it owns measurement persistence and idempotent replay handling.
- Accepted-progress delivery treats `Applied` and `Duplicate` as success. Invalid, unsupported-schema, and poison outcomes become sanitized bounded failures for the existing retry/dead-letter path; unexpected consumer or persistence exceptions propagate for retry. Logs omit raw answer JSON, photos, device tokens, and payload dumps, while retaining event ID, report submission ID, correlation ID, causation ID, schema version, outcome, retry or dead-letter state, and counts.
- **Background Job Updates**: Added `[DisableConcurrentExecution(60)]` attribute to `EmailJob.ExecuteAsync` to serialize overlapping `EmailJob.ExecuteAsync` executions across worker instances. This reduces concurrent overlap, but exactly-once delivery still relies on the durable notification guard in `EmailJobHandlerService.ProcessAsync` (via `TryTransitionToSendingAsync`) because Hangfire locking is not keyed by `notificationId`.
- Push delivery uses `PushNotificationJob` plus the thin `PushNotificationJobHandlerService` adapter to invoke the Notifications-owned claim/send/state-transition/retry use case. `PushNotificationJob` retains `[AutomaticRetry(Attempts = 0)]` because Notifications persists and schedules deterministic recovery; invalid-token outcomes still tombstone the bound installation.
- Background-created in-app notifications flow through the Notifications-owned `NotificationEventBridge`, so they enqueue durable push intents after persistence in the API composition root. Testing retains that bridge while Worker selects no-op schedulers, preserving durable intent creation without Hangfire execution.
- Recurring job `push-stale-installation-cleanup` marks inactive installations with `DisabledReason=InactiveStale`; it is intended as rollout hygiene and should stay enabled even when outbound send delivery is feature-flagged off.
- Notifications owns `PasswordRecoveryEmailSchedulerAdapter`, mapping the Identity-owned seven-value request to the unchanged Common password-recovery payload and forwarding cancellation to its owner scheduling port. Worker retains the generic Common scheduler forwarding and environment selection.
- Notifications owns `CoachingEmailNotificationSchedulerAdapter`, which implements the provider-neutral email feature and scheduling ports, maps the three Coaching invitation requests to unchanged Common invitation payloads, and forwards cancellation to Notifications-owned generic scheduling ports.
- Coaching email handlers consume public module facts and provider-neutral requests. The Worker retains only generic Common email scheduler forwarding and environment-selected runtime scheduling.
- Push scheduling is selected once by the Worker DI helper: testing uses `NoOpPushBackgroundScheduler`, while non-testing uses `HangfirePushBackgroundScheduler`. Provider delivery remains Notifications-owned FCM.
- The same testing split selects no-op email and action schedulers; non-testing selects their Hangfire implementations. Common job interface targets, method signatures, and recurring IDs remain unchanged.
- The Worker facade owns recurring-job registration and environment scheduler selection while Infrastructure hosts the runtime implementations that consume persisted entities and localized messages. Its retained Infrastructure edge is exercised by the final host facade delegating `AddInfrastructureBackgroundServer()` to the Infrastructure-owned Hangfire persistence implementation.
- Notifications boundary: Worker provides the compatibility adapters, job execution, and scheduler selection. It does not expose Hangfire or Common types through Application's provider-neutral notification contracts; see [`issue-381-notifications-boundary.md`](../docs/modular-monolith/issue-381-notifications-boundary.md).
- The five Coaching in-app command handlers are repository, resource, and culture-free compatibility adapters. They load only public Coaching or Identity facts when needed, submit one `InApp`-eligible Coaching intent, and retain their legacy error logging.
- Task 33 reconciles direct project references without changing provider behavior, endpoints, job or recurring identities, physical entity locations, persistence, or migration behavior.
