# LgymApi.Application.csproj

- Purpose: use-case and business orchestration layer.
- Contains: services, service interfaces, feature repository abstractions, application models, notification abstractions, and module-owned app DI helpers. Shared neutral primitives and technical contracts compile from Platform.
- Public neutral primitives `Result`, `Unit`, `AppError`, and its generic HTTP error types compile only from `LgymApi.Platform/BuildingBlocks`; their established `LgymApi.Application.BuildingBlocks.*` namespaces remain unchanged and `Common` must not provide compatibility aliases for them.
- Rules: own business rules, authorization checks, transactions, and UoW commits here.
- Boundary: do not reference infrastructure implementations or either `LgymApi.BackgroundWorker*` project or namespace.
- Platform background-command ports: `IActionCommand` and `ICommandDispatcher` compile from Platform under their established `LgymApi.Application.Platform.Contracts.BackgroundCommands` namespaces; the 15 feature commands stay in their owning module `Contracts/BackgroundCommands` folders. Worker runtime types must not leak through these contracts.
- `ICommandOutboxWriter` is the stage-only background-command port for use cases that must commit a command envelope atomically with their own state; callers own the shared unit-of-work commit and do not schedule dispatch directly.
- Platform serialization contracts: the canonical persisted-payload `JsonSerializerOptions` and typed-ID converters compile from Platform under their established `LgymApi.Application.Platform.Contracts.Serialization` namespaces; API HTTP JSON reuses the typed-ID converter but keeps its stricter enum input policy.
- Durable command serialization writes the legacy `LgymApi.BackgroundWorker.Common.Commands.*` canonical ID and byte-compatible JSON. Application CLR full names are read aliases only; `CommandEnvelope.CommandTypeFullName` retains its legacy name while storing the canonical ID.
- The closed 15-command Worker registry represents committed system intent. Authorization happens before a command is persisted or scheduled, so Worker replay and dispatch do not re-authorize a historical command as a fresh caller action.
- `ICommandEnvelopeRepository.TryRecoverDuplicateAsync` is invoked by the Application runtime after its save throws. Infrastructure internally classifies only the command-envelope correlation uniqueness violation, detaches the supplied staged envelope, and reloads the winner; all other failures rethrow unchanged.
- DI ownership: `AddApplication` composes the remaining Reporting, Workout & Progress, Coaching, and Nutrition business-service helpers plus the internal Platform command-envelope runtime helper. Platform, Identity, Training Planning, Notifications, Application API adapters, Infrastructure, and Worker retain separate host-facing facades.
- BuildingBlocks, Technical Platform, and Reference Data are internal `Platform / Reference Data` sub-boundaries, not canonical modules or projects. `AddPlatformModule` is the only public Platform facade, and Reference Data must not gain a second public module facade.
- AppConfig protected operations authorize exactly once through the consumer-owned `IAppConfigAuthorizationPort`; its latest-by-platform lookup remains unauthenticated and the service keeps AppConfig repository and UoW behavior unchanged. `IAppConfigRepository` retains its legacy `Repositories` path for source compatibility but is an AppConfig-specific Reference Data port, not generic or Technical Platform surface.
- Notifications policy, provider-neutral contracts, events, lifecycle, delivery, retry, cleanup, and Coaching intent policy compile from `LgymApi.Notifications` while retaining their established `LgymApi.Application.Notifications.*` namespaces. Application owns no Notifications policy registrations.
- The original #381 boundary documentation predates the extraction. Notifications now compiles from its own module assembly; endpoints, durable identities, the shared `AppDbContext`, and the migration stream remain unchanged.
- Training ELO scoring is selected by exercise profile in the training service; legacy exercise create/update methods always use the standard profile while privileged variants can opt into alternate formulas.
- Completed-training execution and history reads are owned by `WorkoutProgress/TrainingExecution`; `ITrainingService` remains the compatibility facade for existing Training API and coaching callers.
- `WorkoutProgress/ProgressData` owns immutable score-chart, measurement, main-record, and ELO read/write models behind `IWorkoutProgressReadWriteService`; legacy feature services remain compatibility facades and API mappings preserve legacy payloads.
- `WorkoutProgress/Errors` owns the Training, Exercise, Exercise Score, Measurement, Main Records, Gym, and ELO Registry error types; they retain their legacy `AppError` bases, status mappings, and messages without Common aliases.
- `WorkoutProgress/Dashboard` owns the public trainer-dashboard read facade. Coaching authorizes the trainer-trainee relationship before passing authorized IDs to it; its training details are explicit read models rather than Training, ExerciseScore, or Exercise entities.
- Workout & Progress cross-module access is limited to its `ProgressData`, dashboard, ranking, training execution/history, and `Contracts/ReportingIntegration` contracts/read models. The production `#386` integration exposes a Workout & Progress-owned idempotent measurement consumer; Reporting stages the separate Reporting-owned command, and legacy routes and payloads remain unchanged.
- Workout & Progress owns seven focused marker-safe persistence ports under `WorkoutProgress/Persistence` for exercises, scores, gyms, measurements, main records, ELO, and completed training. These ports expose `Id<AccountReference>` and immutable persistence models, never Identity entities or broad Identity repositories; Application services retain authorization, transaction, and UoW commit ownership.
- Reporting submission acceptance derives and validates its versioned measurement payload through a persistence-neutral factory and stages the Reporting-owned accepted-progress command through `ICommandOutboxWriter` in the submission unit of work. The committed envelope is dispatched as shared JSON; Workout & Progress validates its own raw wire representation and maps it into its consumer event. Direct measurement persistence is outside the acceptance path.
- The internal Application `CommandEnvelopeRuntime` owns command-envelope lifecycle commits through Platform repository/UoW contracts. On an exact duplicate correlation failure, Infrastructure's internal Npgsql classifier and repository recovery detach only the staged envelope and return the winner; no provider exception types cross the Application boundary.
- Reporting-specific not-found, invalid, and forbidden errors are owned under `Reporting/Errors/`; they retain their BuildingBlocks bases, HTTP status mappings, and resource-backed messages without Common aliases.
- Reporting services consume exactly five focused persistence ports under `Reporting/Persistence`: templates, requests/submissions, recurring assignments, photos/upload sessions, and relationship access. Their immutable models and account IDs are marker-safe; Application owns authorization, transactions, and UoW commit timing.
- `PhotoStorageOptions.LocalDevelopmentSigningKey` is the dedicated configuration seam for Local Development photo bearer capabilities. It is not derived from JWT configuration and is required only by Infrastructure when the Local provider runs in Development.
- Automatic recurring processing uses one outer transaction per candidate, while trainer request-now uses one outer transaction per invocation. Both lock the assignment through `FindByIdForUpdateAsync`, re-evaluate the freshly loaded graph, and share a stage-only creation helper. That helper stages the pending request, assignment pointer/timestamps, and canonical `ReportRequestCreatedInAppNotificationCommand` through `ICommandOutboxWriter.StageAsync`; it never saves, commits, or schedules. The outer use case performs the single `IUnitOfWork.SaveChangesAsync()` and transaction commit.
- Manual request-now bypasses only `NextEligibleAt`. It still requires trainer role and active relationship, assignment ownership, an active start/end window, a non-deleted template, and either no current request or a fully completed `Submitted -> submission -> feedback-added -> feedback-read` lifecycle. Pending, expired, cancelled, incomplete, or missing current-request graphs remain conflicts and are never replaced. Successful manual creation uses the same notification envelope as automatic creation, and the next eligibility date advances only after feedback is read.
- Automatic processing isolates a confirmed pre-commit failure to its assignment: it rolls back, disposes the transaction, emits bounded diagnostics, and continues later candidates. Begin, cancellation, rollback, commit-outcome ambiguity, and disposal failures abort rather than reuse an unsafe context. Recurring diagnostics contain only allowlisted identifiers, outcome/reason values, and exception type names, never report or user content.
- `ReportingService.Photos.Completion.cs` owns the active photo-completion validation, persistence, idempotency, and replaced-object cleanup helpers; it is a live Reporting partial contributor, not a migration shim.
- Accepted-progress operations are observable through event ID, report submission ID, correlation ID, causation ID, schema version, outcome, retry or dead-letter state, and counts. Raw answer JSON, photos, device tokens, and payload dumps are not logging fields.
- Training ELO formulas are implemented as one strategy class per `ExerciseEloFormula` under `Application/WorkoutProgress/Scoring/Elo` and resolved through DI instead of switch logic in `TrainingService`; the pull-up profile rewards lower weight with `PullupWeighted`.
- Enum lookups are the source of truth for front-end choice lists; `ExerciseEloFormula` is exposed through the enum lookup service and should not be duplicated as a hardcoded UI list.
- Enum lookup entries should carry a stable enum-string `id`; `name` and `displayName` should both be translated display text. Front-end choice lists should bind to the lookup `id`.
- `EnumLookupMappingProfile` owns the six supported concrete enum-to-lookup maps; `EnumService` filters hidden values and supplies an explicit culture context when present, otherwise the formatter uses `CurrentUICulture`.
- Application input records for lookup-backed exercise forms should receive already-normalized enum values from API mapping profiles; do not parse lookup ids inside application services.
- Notifications module behavior preserves the marker-only session-disassociation seam, delivery-key and `(installation,type,eventId)` idempotency, retry/cancellation recovery, cursor ordering, eligibility/culture/deeplink policy, and stale-installation audit-preserving cleanup. Notifications is the raw-token and provider implementation boundary; Worker remains the scheduler/runtime boundary.
- Google account unlinking uses `IUserExternalLoginRepository` for active-row lookup plus soft-delete staging so the service layer can tombstone the current Google login without introducing provider-agnostic unlink behavior.
- Identity password recovery owns and consumes `IPasswordRecoveryEmailScheduler` and its seven-value typed request. Worker/Common payloads remain outside that public port, and the service supplies an explicit empty `ResetUrl`.
- Identity user workflows compile from `LgymApi.Identity` and are split across `IUserRegistrationService`, `IUserCredentialLoginService`, `IUserSessionTerminationService`, `IUserProfileService`, `IUserRankingService`, `IUserAdminAccessService`, and `IUserRoleAdministrationService`. API callers use the focused login, session, profile, ranking, and admin contracts; `EloRegistryService` uses registration inside its existing outer transaction.
- Identity owns `IAccountReadService` for immutable active-account facts containing `Id<User> Id`, `Name`, `Email`, `Avatar`, `PreferredLanguage`, `PreferredTimeZone`, and `CreatedAt`, available by ID, normalized email, or ordered ID batch. Reads remain active-only; the ordered batch replays one `IUserRepository.GetByIdsAsync` read in caller order, retains duplicate input IDs, and omits missing or soft-deleted accounts (`null` for unavailable single reads). `AccountReadMappingProfile` owns every `User -> AccountReadModel` transformation. Coaching consumes the immutable `CreatedAt` fact only after identity enrichment to preserve trainer-dashboard `createdAt` sorting parity; this adds no API, route, or schema change. Notifications has no separate account-fact projection while its records remain ID/message based.
- Identity's public assembly additionally publishes marker-only account lookup, access facts, session validation, and authenticated-context contracts. Application adapters rebind only at the Identity persistence seam and use registered mapping profiles for `User` to public fact/context projections; ordered lookup batches preserve caller order and duplicates while omitting unavailable accounts.
- The focused split preserves existing API route, HTTP verb, and payload contracts. `IUserRoleAdministrationService.UpdateUserRolesAsync` remains the focused role-administration use case, while the existing route-backed `IRoleService.UpdateUserRolesAsync` path remains unchanged.
- No monolithic `UserService`, `IUserService`, `IUserServiceDependencies`, or dependency aggregate remains. Focused services use direct constructor injection; high arity is accepted without a numeric cap when it keeps collaborators visible.
- Focused Training Planning Plan, ManagedPlan, and PlanDay workflows compile from `LgymApi.TrainingPlanning` under their established `LgymApi.Application.TrainingPlanning.*` namespaces. `TrainingPlanningModule.AddTrainingPlanningModule` owns their registrations; Application has no retained PlanDay source or registration seam.
- Training Planning owns seven immutable managed-plan contracts under `TrainingPlanning/Contracts/ManagedPlans`. The completed Coaching collaboration slices authorize through `ICoachingRelationshipAccessService` or active-link facts, then delegate to these owner contracts while preserving trainer-template creation, clone versus trainee activation, active-pointer, error, and transaction semantics. `ManagedPlanMappingProfile` is discovered through the explicit TrainingPlanning assembly marker and every `Plan` result projection uses injected `IMapper` with a fresh `MappingContext`.
- Training Planning managed-plan owners use Training Planning `PlanErrors` for validation and missing-plan outcomes; Coaching retains relationship errors only for authorization before delegation.
- Coaching persistence is split into invitation, active-link, unpaged fact-reader, and trainee-note/history ports under `Coaching/Persistence`. Their models are immutable Coaching facts and typed identifiers only; the Application-scanned `CoachingPersistenceMappingProfile` owns all entity/fact and write-model/entity transformations. These focused ports are the sole Coaching persistence registrations; broad Coaching repository and service seams are retired.
- Coaching exposes `ICoachingRelationshipAccessService` to Nutrition and its own collaboration slices. Reporting and Recurring Reporting instead consume their own `IReportingRelationshipAccessPersistence` fact port and immutable authenticated account context, retaining photo self-access, report authorization, commits, notification timing, and accepted-progress outbox ownership without a direct Coaching dependency.
- Training Planning owns PlanDay commands, queries, immutable read/write models, errors, mapping, and registration. Its public `IPlanDayService` uses only account, plan, plan-day, and plan-exercise markers; the internal persistence port projects entity and Workout & Progress data into Planning-owned models. Coaching implements the account-ID-only `IPlanDayRelationshipAccessPort` from `ICoachingRelationshipAccessService`, and `AddCoachingModule` registers the adapter once, preserving owner short-circuit authorization without a Training Planning-to-Coaching dependency.
- Workout & Progress composition owns the adapters for Training Planning's `IPlanExerciseCatalogPort`, `IPlanExerciseClonePort`, and `IPlanTrainingActivityPort`. They are the only Application-side rebind from Planning/account markers to the existing Exercise and Training repositories; they stage exercise copies without commits or transactions. Workout execution, history, exercise-history, and gym-last-training reads consume Planning's active-only `IPlanDayReferenceReadService` facts rather than PlanDay entities; marker-to-entity rebinding remains in persistence.
- Workout & Progress owns the ID-only `IMeasurementsRelationshipAccessPort` under `WorkoutProgress/Contracts/Measurements`; Coaching implements and registers its adapter, which projects the marker relationship-access contract to the active-relationship boolean without adding a Workout & Progress-to-Coaching dependency. `MeasurementsService` uses Identity account facts and this port for trainer authorization without taking a dependency on Identity entities or repositories.
- Coaching invitation creation, email creation, unexposed list, paginated list, and public-status operations are focused contracts under `Coaching/Invitations`. They use only typed IDs, Coaching facts, and Identity account facts; the paginated slice enriches unpaged invitation facts before filtering, sorting, counting, and paging. The anonymous public invitation API calls `IPublicInvitationStatusUseCase` directly, which rejects missing, invalid, and expired invitation capabilities with the same non-disclosing not-found result before bound-trainee detection or Identity email-account resolution.
- Coaching invitation acceptance, rejection, and revocation are focused one-method contracts under `Coaching/Invitations`. Accept and reject validate a bound trainee ID or normalized email through Identity facts without mutation; an expired pending email invitation stages only `Expired` plus `RespondedAt`, stays unbound, creates no link, and queues no command. Valid pending email acceptance or rejection binds immediately with its staged response, while accepted replay, link-conflict mapping, revocation ownership, command timing, and UoW boundaries retain legacy behavior.
- Coaching relationship unlink, trainee detach, and current-trainer reads are focused one-method contracts under `Coaching/Relationships`. Their immutable inputs carry only typed user IDs; unlink authorizes through the Coaching relationship-access contract and sends no notification, detach commits the staged link removal before queuing the existing relationship-ended command, and current-trainer profile enrichment uses active Identity account facts plus the registered relationship mapping profile. Trainee relationship API actions call these focused contracts directly; the broad relationship facade and dependency bag are removed.
- Coaching trainer-dashboard reads combine complete unpaged Coaching facts with one ordered Identity account batch, capture one `now`, map the enriched logical rows through `TrainerDashboardMappingProfile`, and only then apply search, relationship/status filters, deterministic sorting, counting, and paging. Five focused `Coaching/Progress` contracts authorize through the Coaching relationship-access seam before one `IWorkoutProgressDashboardReadService` call and preserve its established read models and not-found translation.
- Seven focused `Coaching/ManagedPlans` collaboration contracts authorize trainer operations through `IMarkerCoachingRelationshipAccessService`; the trainee active-plan read verifies its Coaching active-link fact through a marker-ID query. Each slice maps its immutable reference-ID input through `ManagedPlanCollaborationMappingProfile`, delegates exactly once to the corresponding Training Planning managed-plan owner contract, and passes through the owner's result, error, clone, active-pointer, and transaction semantics.
- Coaching trainer-note list, create, update, delete, and history operations plus trainee-visible list and detail reads are focused one-method contracts under `Coaching/TraineeNotes`. Their immutable inputs carry trainer, trainee, and note typed IDs plus shared immutable upsert data; `TraineeNoteMappingProfile` owns fact, write, and read transformations. Trainee-visible reads use the existing visible, non-deleted, trainee-owned persistence semantics without relationship authorization or commits. Create, update, and soft delete stage the note and immutable history row before one owner `IUnitOfWork` commit, then create and update dispatch the existing notification command only after a successful commit under the legacy visibility-transition rules. Trainer and trainee note API actions call these focused contracts directly; the broad note facade is removed.
- Nutrition Supplementation exposes nine focused public contracts under `Nutrition/Supplementation`; their internal use cases are registered exactly once by `AddNutritionModule`. Intake check-off validates against no-tracking active-plan data, mutates a tracked existing intake, and reloads a uniqueness-race winner without a second save.
- Nutrition owns 18 focused public use cases: Diet D1-D9 under `Nutrition/DietPlans` and Supplementation S1-S9 under `Nutrition/Supplementation`. Their inputs and read models use typed IDs and immutable Nutrition data, implementations are internal, and `AddNutritionModule` registers every contract exactly once.
- `Nutrition/Errors` owns the Supplementation not-found, invalid, and forbidden errors; their BuildingBlocks bases, localized messages, and HTTP status mappings remain unchanged without Common aliases.
- Nutrition consumes only `ICoachingRelationshipAccessService` for trainer/trainee facts. It owns access adaptation, validation order, commits, lifecycle rules, Diet history, and command timing; its persistence ports separate no-tracking reads from tracked mutations, while the use case owns the single UoW save and no repository owns transactions.
- The sole intentional post-cutover semantic difference is Diet behavior for a nonempty trainee ID: after action-specific prevalidation, a non-trainer receives the existing localized trainer-role 403. All other preserved Diet and Supplementation behavior remains compatibility constrained.
- This Application cutover leaves Worker behavior and its project document, DataSeeder behavior, every `.csproj`, and the root Project Purpose Map unchanged.
- API adapters are physically owner-oriented under Identity, Training Planning, Coaching, Reporting, Nutrition, Platform / Reference Data, and Workout & Progress paths. `ApplicationApiAdapterServiceCollectionExtensions.AddApplicationApiAdapters` registers the exact 25 scoped Application adapter contracts after Infrastructure; their implementations remain internal. Notifications-owned API adapters are added separately by `AddNotificationsApiAdapters` with exactly three scoped contracts. Coaching publishes five and Reporting six controller-facing API ports from their owner `ApiAdapters` folders. Workout & Progress keeps only `IExerciseApiAdapter` and `IMainRecordsApiAdapter` for owner input-model construction; Gym, Measurements, Exercise Scores, Training, and ELO Registry controllers consume owner services directly.
- Identity application workflows and their required contracts compile from `LgymApi.Identity`; `AuthenticatedAccountApiAdapter` delegates token, logout, deletion, ranking-visibility, and time-zone operations through Identity's marker-only `IAuthenticatedAccountCompatibilityPort` rather than loading `User` through an Identity repository. Remaining Application code consumes compatible namespaces through the existing Application-to-Identity edge, while the API adapter contracts and implementations remain in owner-oriented Application paths.
- Application service constructors expose their collaborators directly; no Application dependency aggregate remains. This keeps Reporting, Workout & Progress, and Training persistence and transaction dependencies visible without changing their public service contracts.
- ADR-007 records the final compatibility commitment: the 25 Application API adapters preserve external contracts while migration-era `Task7`, `ApiCompatibility`, and `Compatibility.Task7` CLR adapter identities remain absent. Established non-Task7 Application namespaces remain only where source or wire compatibility requires them, and need an approved consumer-inventoried migration before removal.
- Nutrition and Coaching expose separate trainee-owned history reads: active diets require matching trainee ownership, while note history requires current visibility and consumes only revisions marked visible to the trainee.
