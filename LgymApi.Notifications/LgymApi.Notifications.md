# LgymApi.Notifications.csproj

- Purpose: stable code boundary for provider-neutral notification capabilities.
- Contains: provider-neutral Notifications contracts, read models, errors, event bridge, installation lifecycle, in-app fanout, push enqueue/delivery/retry/cleanup, Coaching intent policy, and the email provider/template stack. Established non-Task7 `LgymApi.Application.Notifications.*` namespaces remain source-compatible, but their policy implementation compiles from this assembly.
- Rules: keep direct references limited to BackgroundWorker.Common, Domain, Identity, Platform, and Resources. Its internal persistence seam and private provider configuration are friend-visible only to Infrastructure, UnitTests, and IntegrationTests.
- Boundary: do not add a DbContext, migrations, publicly exposed provider credentials, or a reverse Identity dependency. `INotificationsPersistenceContext` exposes only its five owned sets and typed entries for in-app and push messages.
- Account lifecycle integration: Notifications registers the scoped `PushInstallationSessionDisassociationAdapter` for Identity's `IAccountSessionDisassociationPort` and `PushInstallationAccountCleanupAdapter` for `IAccountPushInstallationCleanupPort`. The adapters, lifecycle service, and repository contract forward only marker IDs; private persistence rebinds IDs, stages session disassociation or all account-linked installation deletion without committing, and leaves Identity's UoW boundary authoritative. Account cleanup stages dependent PushNotificationMessages before their installations, retaining the configured cascade as relational safety.
- EF coordination: `NotificationsModelConfigurationRegistrar` owns the five fixed-order mappings. Infrastructure retains the global phase coordinator, the single `AppDbContext`, migrations, and the scoped `INotificationsPersistenceContext` alias without assembly scanning.
- Composition: `NotificationsModule.AddNotificationsModule` is the policy and repository-registration facade; its configuration overload is the sole public email/provider registration path and validates/adds the private email stack plus FCM client, settings, retry mapping, and provider sender. `AddNotificationsApiAdapters` separately registers the three Notifications-owned API adapters after Infrastructure composition. Repositories use only `INotificationsPersistenceContext`, stage changes, and preserve the configured email send lease through Infrastructure's narrow `AddNotificationsInfrastructure()` settings bridge. API binds the SignalR publisher as the host adapter, and Worker remains last for scheduler and runtime selection.
- Email templates: the twelve source files are under `EmailTemplates/<Template>/<en|pl>.email`; API and Integration projects link them to the unchanged `AppContext.BaseDirectory/EmailTemplates/<Template>/<en|pl>.email` runtime layout.
- Compatibility: preserve `DeliveryKey`, `(installation,type,eventId)`, cursor ordering, bounded retry/cancellation recovery, stale tombstoning, and Coaching's single eligible channel. Public contracts remain free of Worker/Common runtime types, provider credentials, and provider-private token handling; FCM credentials and tokens remain internal to Notifications.
- Retention: `PushNotifications` owns normalized defaults for message history (30 days), disabled installations (30 days after `DisabledAt`), and in-app notifications (90 days), plus a 500-row purge batch. Non-positive configured values normalize to those defaults through `PushNotificationOptionsFactory`; non-numeric option values fail configuration binding. Retention settings stay internal to Notifications; Common contains the corresponding parameterless job interfaces without payloads or provider types. Retention repositories accept caller-computed UTC cutoffs and positive candidate limits, select bounded oldest-first candidates including soft-deleted rows using `CreatedAt` for messages/in-app notifications or non-null `DisabledAt` for installations, then stage `RemoveRange` without committing. Disabled-installation selection excludes active and logout-disassociated-only rows. All three cleanup services drain bounded batches in one invocation and own one unit-of-work commit for each staged batch. Start logs contain only operation, cutoff, and configured batch size; success and failure add deleted count, batch count, and duration, while failure also carries the exception through the configured sensitive-data enricher. Account deletion separately stages immediate removal of all account-linked LGYM installations and dependent push history, while logout only disassociates the ended session. These database guarantees do not delete or set retention for Firebase tokens or Firebase Installation data; mobile clients own that provider lifecycle.
- Final adapter disposition: `AddNotificationsApiAdapters` registers exactly three controller-facing owner contracts. `PushInstallationSessionDisassociationAdapter`, `CoachingEmailNotificationSchedulerAdapter`, and `PasswordRecoveryEmailSchedulerAdapter` remain as focused integration adapters. Their removal requires an approved replacement that preserves contracts, registrations, consumers, and durable behavior. Notifications services use direct constructor injection with no numeric arity cap; dependency aggregates and service location remain forbidden.
